The part that is not a rename

A step with no write tool
cannot write.

The usual way to build a refund bot: list ten checks in the prompt, then hand the agent a refund tool. You just gave it the power to move money, plus a note about when to use it.

STEP 1 / DECIDE

+ read order
+ read customer
× issue refund
GATE
eligible?

STEP 2 / ACT

+ read order
+ issue refund

The refund tool does not exist in step 1. It arrives in step 2, after the check passed, scoped to one customer and usable once.

Three rules, whole model

Node, edge, verdict.

NODE

A subprocess

One run of one command line. Any agent CLI, or any plain shell command.

EDGE

A file

A node's output lands on disk and drops into the next node's prompt.

VERDICT

The exit code

Zero is success. Never the agent's own JSON, for the reason below.

The graph above, written down

# how to run something
[agents.dev]
argv = ["claude", "-p"]

# what to run
[nodes.implement]
agent   = "dev"
isolate = true       # own checkout
prompt  = "Add request-id logging."

[nodes.verify]
needs  = ["implement"]  # the edge
gate   = true          # stops the run
prompt = "npm test"

What you see

$ python geng.py run graph.toml

wave 1  (1 node, 4 at a time)
  ok   implement
wave 2  (1 node, 4 at a time)
  GATE verify exit=1

halted: gate failed: verify

Swap claude -p for codex exec and nothing else moves. One line is the whole portability story.

Because it goes missing

So the exit code is the verdict. Your agent's JSON still flows to the next node as data. It just never decides whether a step worked.

Scheduling

Independent steps share a row.

WAVE 1
audit api
audit web
audit docs
WAVE 2
merge findings
WAVE 3
typecheck + test
three 2s steps, run together: 2.3s run one after another: 6s

geng groups everything with satisfied dependencies into one wave. Row 2 waits for all of row 1.

Run it twice and the second run reports cached in a fifth of a second. Change one prompt and only that step and the ones after it repeat, because each key is a hash of its prompt, its command, and its ancestors.

Parallel writers

Two steps, one file,
no collision.

geng/api ctx.log
geng/web ctx.log
your branch untouched

isolate = true gives each step its own git worktree and branch. Work commits only if the step passed, so a broken attempt never looks reviewable.

Then merge the branch you like. The one rule: one file, one owner. Worktrees prevent collisions, not disagreements.

How Context file

Before any real run, look at the commands

python geng.py plan graph.toml       # diagram and waves, runs nothing
python geng.py run graph.toml --dry-run   # exact command per node

--dry-run writes nothing, spends nothing, and prints the precise command each node would execute. Last checkpoint before an agent touches your repository.

[agents.review]
argv = ["claude", "-p", "--allowedTools", "Read,Grep,Glob"]
Two traps, both found by testing rather than reading. For omp the read only boundary is --approval-mode always-ask; --tools looks like it restricts capability and does not. For gate nodes skip bash -lc: on Windows with WSL installed and no distro it resolves to a stub that fails, so your gate fails for a reason unrelated to your tests.

Read this before you adopt it

Most jobs want a loop.

TRIGGER 1

Context rot

One window is hitting 300k to 500k tokens per pass.

TRIGGER 2

Real review

The stakes rule out the author being the judge.

TRIGGER 3

Wall clock

Independent work is queued behind itself for no reason.

None of those? Keep your loop.

A graph costs you several prompts instead of one, a state schema between steps, and a fresh class of routing bugs. Agents burn about 4× the tokens of chat, multi agent setups about 15×. Anthropic's own guidance: most coding tasks have fewer truly parallel parts than research does.

The risk that actually bites is agreement. Twenty agents on one model reading one flawed context will agree at scale. A graph multiplies a shared mistake as efficiently as good work. The only defence is an edge touching reality, tests that ran or a build that compiled, which is what a gate is for and why a second reviewer belongs on a different model. Your review bandwidth is the ceiling, not the concurrency limit.

Claims with receipts.

  • Editing one prompt invalidates that step and its descendants, nothing else.
  • A failed gate halts the run; dependents skip rather than run.
  • An undeclared placeholder fails its node instead of rendering empty.
  • Two isolated steps writing one file commit to separate branches.
  • A failed isolated step publishes no commit.
  • A second concurrent run is refused, not allowed to corrupt state.
  • --dry-run leaves no artifacts, no state, no worktrees.

Short answers

Likely questions.

Is graph engineering just a rename?
Mostly. The term is days old and started as a tweet; the structure is 19 months older, and Anthropic ships it as dynamic workflows without using the word. Per step capability is the part that is new. Background.
Why not LangGraph, Temporal, Make, Actions?
Use them if you run them already, they are all more capable. None is one file you drop beside a repo with no infrastructure.
Do I need git?
Only for isolated steps. The rest works without it, and the tests skip their git cases when it is absent.
Why no pip install?
The premise is one file, no dependencies. A package would contradict it.
Can one graph mix vendors?
Yes, and that is the point of the second reviewer. A different model is the cheapest defence against agreement.
Is someone else's spec safe to run?
No more than their Makefile is. A spec is executable code. Security notes.
