Run coding agents as a graph, not a loop.

One agent looping over ten jobs forgets the early ones, then grades its own homework. A graph gives each step a clean context and only the tools it needs — and lets a test command, not an agent, decide whether the work is any good.

curl -O https://raw.githubusercontent.com/AdityaIndoori/graph-engineering/main/geng.py
python geng.py run examples/smoke.toml

The problem this solves

You have an AI coding agent and a real job for it: add request-id logging to the HTTP layer, then make sure the tests still pass.

The obvious approach is to hand one agent the whole job and let it iterate until it says it is done. People call that a loop. Two things go wrong with it, and both are structural — neither is fixable by writing a better prompt.

It forgets
Everything the agent does piles into one context window. Once that window is in the hundreds of thousands of tokens, the early work is effectively out of view. On a forty-file change, file three is forgotten by file thirty.
It grades its own homework
The same agent that wrote the code decides whether the code is good, and reports success. This is the more damaging of the two: you cannot trust the verdict, because the thing being judged and the judge are the same thing, with the same blind spots and the same motivation to be finished.

The idea

Split the job into separate steps. Each step is its own agent run with its own fresh context, and the steps connect in a defined order. That is a graph.

plancannot write
→
implementown workspace
→
npm testgate
→
reviewcannot write

Both problems above now have an answer. Forgetting is solved because every step starts with a clean context holding only what it was explicitly given. Self-grading is solved because the third step is not an agent — it is your actual test suite, which returns pass or fail and cannot be talked out of it.

And splitting the work buys a third thing a loop cannot offer. Because each step is a separate invocation, each step can be given different capabilities. The review step is handed no editing tools at all, so it physically cannot “helpfully” fix the thing it was asked to judge. It has to tell you instead.

Why per-step capability is the part that matters

The standard way to build a refund bot is to write instructions listing ten checks a refund must pass, then give the agent a tool that issues refunds.

What you have actually done is hand it the power to move money, with a polite note about how you would prefer that power be used. It works only if the agent reads the instructions, follows them in order, targets the right customer, and nobody slipped anything misleading into its context.

Split it into two steps and the checking step does not have the refund tool at all. The capability arrives only after the check has passed. That is a boundary rather than a request — and everything below exists to make that boundary one line of config.

What geng is

geng.py is a single Python file, about 600 lines, standard library only. You describe the graph in TOML; it runs the steps in dependency order, runs independent ones at the same time, stops when a gate fails, and remembers what already succeeded so a re-run skips it.

If you have used make or a GitHub Actions workflow, it is that — except the steps are agent invocations rather than compile commands. Three sentences define the whole model:

A node is a subprocess
One node is one run of one command line.
An edge is a file
A node's output is captured to disk and substituted into the prompts of nodes that declared a dependency on it.
The exit code is the contract
0 means success, anything else means failure. Why that and not the agent's output is worth two paragraphs of its own.

The graph above, as a spec

[agents.dev]
argv = ["claude", "-p", "--permission-mode", "acceptEdits"]

[nodes.implement]
agent   = "dev"
isolate = true                  # its own git worktree and branch
prompt  = "Add request-id logging to the HTTP layer."

[nodes.verify]
needs  = ["implement"]           # the edge
agent  = "shell"
gate   = true                  # a failure here halts the run
prompt = "npm test"
$ python geng.py run graph.toml

wave 1  (1 node(s), 4 at a time)
  ok   implement
wave 2  (1 node(s), 4 at a time)
  ok   verify

2/2 ok, 0 failed, 0 skipped

Change claude -p to codex exec and nothing else in the file moves. That one line is the whole portability story, and the next section explains why it can be that simple.

Why the exit code, and not the agent's output

After every node, geng has to answer one question: did that step succeed? There are only two possible sources for the answer.

The first is to read what the agent printed — most can emit structured JSON with a status field. The second is the process exit code, which every program on every operating system returns, and where 0 has meant success since Unix.

geng uses the exit code, because the first option does not survive contact with reality:

  • Cursor emits no valid JSON when it fails — so the exact moment you most need to detect a failure is the moment your parser gets garbage.
  • Kiro and aider have no JSON mode at all. There is nothing to parse.
  • Claude Code, Codex and Gemini all offer JSON, in three mutually incompatible shapes. That is three parsers to write and keep working.

So JSON is worth knowing about just long enough to reject it as a success signal. Exit codes are the one thing every tool in the table below already agrees on — which is precisely why switching harness is a one-line change. You can still use an agent's JSON, since geng passes whatever a node prints to the next node. It just never uses it to decide whether the node worked.

How the pieces fit together

Four properties follow from those three sentences, and each one closes a specific gap introduced above.

Files carry state between steps, not context windows
Each node's output lands in .geng/out/<node>.txt and is substituted into dependent prompts as {node}. Referencing a node you did not declare is a hard error, not an empty string — so a graph cannot quietly look connected while passing nothing. This is what makes the clean-context claim real rather than aspirational.
Capability is set per node
Because a node is just a command line, a read-only reviewer is simply a different command line. That is the refund-bot boundary, in one line of config.
Isolated nodes get their own git worktree
A separate checkout on its own branch, so two nodes can edit the same file at once without touching each other or your working directory. Work is committed only if the node succeeded — a half-finished edit can never be mistaken for something reviewable.
Resume is keyed on content
sha256(id + prompt + argv + upstream keys). Edit one prompt and --resume re-runs exactly that node and its dependents. Because a failure costs one node instead of the whole run, many small nodes beat one big one.

Or just run it, in 60 seconds

You do not need an AI agent installed. The bundled example uses Python subprocesses as its agents, so the machinery is visible without spending a token.

git clone https://github.com/AdityaIndoori/graph-engineering
cd graph-engineering
python geng.py run examples/smoke.toml

You should see 6/6 ok, 0 failed, 0 skipped. Read that output against the model above: three nodes had no dependencies so they ran together in wave 1, a fourth waited for all three and received their output through {placeholder} edges, a gate checked the result, and one node failed twice before passing to demonstrate retries.

Then run it again with --resume: every node reports cached in about a fifth of a second. Change one prompt and only that node and its dependents re-run.

python geng.py plan examples/smoke.toml      # diagram + waves, runs nothing
python geng.py run examples/smoke.toml --dry-run   # exact command per node

--dry-run is the habit worth forming: it prints the precise command every node would execute and changes nothing. It is your last checkpoint before an agent touches your repository.

Use the harness you already have

Every one of these exposes a non-interactive command and a meaningful exit code, which is all geng needs.

HarnessAdapter argv
Claude Code["claude", "-p"]
Oh My Pi["omp", "-p", "--no-session"]
OpenAI Codex["codex", "exec"]
OpenCode["opencode", "run", "--auto"]
Kiro CLI["kiro-cli", "chat", "--no-interactive"]
Gemini CLI["gemini", "-p"]
Cursor["cursor-agent", "-p", "-f"]
Amp["amp", "-x"]
aider["aider", "--yes-always", "--message"]

Each also gets a read-only twin, which is how the capability boundary from earlier is actually enforced:

[agents.review]
argv = ["claude", "-p", "--allowedTools", "Read,Grep,Glob"]
Two cautions, both found by testing rather than reading docs. For omp, the read-only boundary is --approval-mode always-ask; --tools looks like it restricts capability and does not. And for gate nodes, avoid ["bash", "-lc", …]: on Windows with WSL installed but no distro it resolves to a stub that fails, so your gate fails for a reason unrelated to your tests. Invoke the tool directly with prompt_via = "none".

When not to use this

Most work does not need a graph, and on this point the people selling the idea agree with the sceptics. Everything above only pays off under three conditions:

1. Context rot
A single agent's window is hitting 300–500k tokens per iteration.
2. Independent review
The stakes are high enough that the author must not be the judge.
3. Wall-clock
Genuinely independent subtasks are running one after another for no reason.
Otherwise, keep your loop. A graph costs you several prompts to maintain instead of one, a state schema between nodes, and a new class of routing bugs. Agents burn roughly 4× the tokens of chat and multi-agent systems roughly 15×. Anthropic's own guidance: “most coding tasks involve fewer truly parallelizable tasks than research.”
And the failure mode to actually fear is not cost. It is correlated error: twenty agents on the same model reading the same flawed context will agree with each other at scale. A graph multiplies a shared mistake exactly as efficiently as it multiplies good work. The only defence is an edge that touches reality — tests that ran, a build that compiled — which is what a gate node is for, and why a second reviewer belongs on a different model. Your review bandwidth, not the tool's concurrency limit, is the real ceiling.

Proof, not claims

53 tests run on Linux, macOS and Windows across Python 3.11–3.13. They pin the properties that would otherwise just be marketing:

  • editing one prompt invalidates that node and its descendants, nothing else
  • a failed gate halts the run; dependents are skipped, not silently run
  • an undeclared {placeholder} fails its node instead of rendering empty
  • two isolated nodes writing the same file commit to separate branches while the main checkout stays untouched
  • a failed isolated node publishes no commit
  • a second concurrent run is refused rather than corrupting shared state
  • --dry-run creates no artifacts, no state and no worktrees

Read the suite · read the whole tool — it is one file, short enough to audit in a sitting.

Questions you are probably about to ask

Is “graph engineering” just a rename?
Mostly, yes. The term is days old and started as a tweet; the structure is 19 months older, and Anthropic ships it as “dynamic workflows” without using the word. The one genuinely new part is setting capabilities per node — the refund-bot argument above. Full background.
Why not LangGraph, Temporal, Make or GitHub Actions?
Use them if you already run them; they are all more capable. geng exists because none of them is a single file you drop next to a repo with no infrastructure at all.
Do I need git?
Only for isolate = true nodes. Everything else works without it, and the test suite skips its git tests when it is absent.
Why is there no pip install?
Because the premise is one file with no dependencies. Publishing a package would contradict it.
Can one graph use agents from different vendors?
Yes, and that is the point of the second reviewer. Define two adapters and give one node each — a different model is the cheapest defence against correlated error.
Is a graph spec safe to run from someone else?
No more than a Makefile is. A spec is executable code; treat it that way. See SECURITY.md.
